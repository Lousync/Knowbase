# 应用层协议

> 《计算机网络》· 应用层

### 域名系统 DNS(重要度:★★★★)

#### DNS 是什么

**DNS**（Domain Name System，域名系统）把人类好记的域名（如 `www.example.com`）转换成机器需要的 IP 地址。它运行在 UDP 端口 53，超过 512 字节的响应改用 TCP 端口 53。

DNS 属于应用层协议，为万维网、电子邮件等几乎所有互联网应用提供名字解析服务。

域名空间按根、顶级域、二级域等层次组织。不同层级的域名服务器只负责自己掌握的区域，解析过程通过逐级转介找到保存最终记录的权限域名服务器。

> 💡 **DNS 为什么用 UDP**
>
> 大部分 DNS 查询只需一问一答，报文短（几十到几百字节），UDP 无连接、开销低，更适合。TCP 只在报文超长或区域传输时使用。

#### 递归查询与迭代查询

递归查询要求被询问的服务器返回最终结果或错误。

迭代查询允许服务器返回自己知道的最佳下一跳。

主机通常向**本地域名服务器**递归查询，本地域名服务器再逐级进行迭代查询。

### 文件传输协议 FTP(重要度:★★★★)

#### FTP 控制连接与数据连接分离

**FTP**（File Transfer Protocol，文件传输协议）在客户端和服务器之间传输文件。FTP 最显著的设计是控制命令和数据传输走两根独立的 TCP 连接：

1. **控制连接**：端口 21，负责传命令和返回结果，在整个 FTP 会话期间始终保持。
2. **数据连接**：每次传文件时按需建立，传完就关。

> 💡 **HTTP vs FTP**
>
> HTTP 的命令（GET/POST）和数据走同一根连接，FTP 把命令和数据分开（两根连接），这叫"带外控制"。优点：可以中途取消文件传输而不用关闭整个会话。FTP 是有状态的（记住登录用户），HTTP 是无状态的。

#### 主动模式与被动模式

**主动模式**（PORT）：客户端先开一个端口，通过控制连接把 IP 和端口告诉服务器，然后服务器从自己的端口 20 主动向该端口发起数据连接。如果客户端在防火墙/NAT 后面，服务器主动连过来会被阻挡。

**被动模式**（PASV）：客户端发送 PASV 命令，服务器开一个临时端口并把 IP 和端口告诉客户端，然后客户端主动向该临时端口发起数据连接。

这种方式所有连接都由客户端发起，不受客户端防火墙限制，现代 FTP 默认都用被动模式。

**对比**：

| | 主动模式 PORT | 被动模式 PASV |
|--|-------------|-------------|
| 谁发起数据连接 | 服务器（端口 20）| 客户端 |
| 适用场景 | 客户端无防火墙 | 客户端有防火墙/NAT |
| 谁开临时端口 | 客户端 | 服务器 |


![示意图](attachment://vault/51cf0aa1-cde1-439c-8700-e50560d353d3/kb-ftp-modes-fig.svg)

#### FTP 工作流程

1. 客户端 TCP 三次握手连服务器的端口 21，建立**控制连接**。
2. 服务器返回 220 就绪码，客户端发 USER 用户名和 PASS 密码进行认证。
3. 需要传文件时：客户端发 PORT 或 PASV 指定模式，双方协商数据连接的临时端口。
4. 建立**数据连接**，完成文件 LIST / GET / PUT 操作后立即关闭数据连接。
5. 控制连接继续保持。下一次传文件时再从步骤 3 重复。
6. 客户端发 QUIT 命令关闭控制连接，FTP 会话结束。

### 电子邮件(重要度:★★★★)

#### 电子邮件系统的组成

电子邮件系统由三个主要部分组成：

1. **用户代理**（MUA）：如 Outlook、Gmail App。
2. **邮件服务器**（运行 MTA/MDA）：中转和存储邮件。
3. **邮件传输协议**：SMTP 送信，POP3/IMAP 取信。

一封邮件的旅程：

1. 发送方用 MUA 写好信。
2. MUA 把邮件推给**发送方邮件服务器**（SMTP）。
3. 发送方服务器经互联网把邮件逐跳推到接收方邮件服务器（SMTP）。
4. 邮件存在接收方服务器上。
5. 接收方用 POP3 或 IMAP 从自己的服务器下载。

分工：**SMTP 负责推（Push），POP3/IMAP 负责拉（Pull）**。

![示意图](attachment://vault/51cf0aa1-cde1-439c-8700-e50560d353d3/kb-email-arch-fig.svg)

> ⚠️ **发送和接收不是同一个协议**
>
> 收发邮件可不是用的同一个协议。发送用 SMTP（推），接收用 POP3 或 IMAP（拉）。

#### SMTP 和 MIME

**SMTP** 使用 **TCP** 端口 25（或提交端口 587），以 ASCII 明文交互。客户端先与服务器建立 TCP 连接，服务器返回 220 准备就绪，然后依次发送命令：

1. HELO（打招呼）。
2. MAIL FROM（发件人）。
3. RCPT TO（收件人）。
4. DATA（正文，以只含一个点的行结束）。
5. QUIT（退出）。

SMTP 只能传输 7 位 ASCII 文本，不支持图片、中文、附件。这些非 ASCII 内容由 **MIME**（多用途互联网邮件扩展）编码后嵌入邮件体，SMTP 原封不动传输。

**MIME**（Multipurpose Internet Mail Extensions）打破 SMTP 只能传 7 位 ASCII 的限制：把非 ASCII 内容（中文、图片、音频、附件、二进制文件）按一定编码规则（如 **Base64**、**Quoted-Printable**）转换成 7 位 ASCII 文本，嵌入邮件体，SMTP 就能原封不动传输。接收方按同样规则解码还原成原始内容。

> 💡 **MIME 不是协议**
>
> MIME 是一种扩展编码标准，让 7 位 ASCII 的 SMTP 能传输中文、图片、附件。它定义编码规则（Base64、QP），不是传输协议。

#### POP3 与 IMAP——收信协议对比

**POP3**（TCP 端口 110）：非常简单的"下载-删除"模型。用户把服务器上的所有新邮件拉到本地，拉完服务器上可以删也可以保留。离线阅读能力强，但多设备同步很差：手机拉完了，电脑上就看不到了。

**IMAP**（TCP 端口 143）：邮件一直留在服务器上，客户端只是远程操作（标记已读、移动到文件夹、搜索等）。天然支持多设备同步：手机、电脑、平板看到的邮件状态完全一致。缺点是需要一直在线，占用服务器存储。

**三协议对比**：

| | SMTP | POP3 | IMAP |
|--|------|------|------|
| 方向 | 发送（推）| 接收（拉）| 接收（拉）|
| 端口 | 25/587 | 110 | 143 |
| 邮件存储 | 不存，只转发 | 拉完可删 | 一直留服务器 |
| 多设备 | 不需要 | 差 | 好 |

### 万维网与 HTTP(重要度:★★★★★)

#### C/S 与 P2P 两种网络应用架构

网络应用（Application）运行在端系统上，通信方式决定了应用的架构。408 主要考察两种：

1. **客户/服务器（C/S）架构**。
2. **对等（P2P）架构**。

![示意图](attachment://vault/51cf0aa1-cde1-439c-8700-e50560d353d3/kb-http-arch-2.svg)

**C/S 架构**：服务器 7×24 小时持续运行、有固定 IP 地址（方便客户找到它），客户间不直接通信。

好处是服务器集中管理、安全性好。缺点是服务器是瓶颈，客户多了会过载，且需要专门维护服务器。

**P2P 架构**：没有固定的服务器，每个节点（peer）同时充当客户和服务器，从其他节点获取资源的同时也把资源提供给别人。

好处是可扩展性强：节点越多，能提供的带宽和资源也越多，不会有单点瓶颈。缺点是管理和安全困难（节点身份不可控）。

> ⚠️ **C/S 与 P2P 的本质区别**
>
> C/S：有中心、客户靠服务器、客户之间不通信；P2P：无中心、节点互为服务器、可扩展但难管理。

#### URL 结构与 HTTP 报文格式

**URL**（统一资源定位符）格式：`协议://主机:端口/路径`。

例如 `http://www.example.com:80/index.html`：协议是 HTTP，主机域名是 `www.example.com`（需 DNS 解析成 IP），端口是 80（HTTP 默认，可省略），路径是 /index.html。

**HTTP 请求报文**由三部分构成：

1. **请求行**：方法 + URL + 版本，如 `GET /index.html HTTP/1.1`。
2. **首部行**：Host、User-Agent、Connection 等键值对。
3. **空行 + 实体体**：GET 通常为空，POST 放表单数据。

**HTTP 响应报文**也分三部分：

1. **状态行**：版本 + 状态码 + 短语，如 `HTTP/1.1 200 OK`。
2. **首部行**：Content-Type、Content-Length 等。
3. **空行 + 实体体**：HTML 页面内容。

#### HTTP 方法与状态码

**HTTP 方法**：请求行第一个词，告诉服务器要对资源做什么操作。

| 方法 | 含义 | 有无请求体 |
|------|------|-----------|
| **GET** | 获取资源（幂等）| 无 |
| **POST** | 提交数据（处理表单/上传）| 有 |
| **HEAD** | 只返回首部，不返回实体体 | 无 |
| **PUT** | 上传/替换指定资源 | 有 |
| **DELETE** | 删除指定资源 | 无 |

**HTTP 状态码**：响应状态行的三位数，按范围分类：

| 范围 | 含义 | 常见例子 |
|------|------|---------|
| 1xx | 信息 | 100 Continue |
| **2xx** | **成功** | **200 OK、204 No Content** |
| **3xx** | **重定向** | **301 永久移动、302 临时移动、304 Not Modified** |
| 4xx | 客户端错误 | 400 Bad Request、403 Forbidden、**404 Not Found** |
| 5xx | 服务端错误 | 500 Internal Server Error、503 Service Unavailable |

#### 非持续连接与持续连接

**非持续连接**：HTTP/1.0 默认方式。每个对象（HTML 页面 + 每个图片/CSS/JS）都单独建一条 TCP 连接，传输完立即关闭。N 个对象需要 N 次 TCP 三次握手，开销大。

**持续连接**：HTTP/1.1 默认方式（Connection: keep-alive）。一条 TCP 连接上可以连续请求多个对象，不用重复握手。

1. **非流水线方式**：一个对象应答完再请求下一个，每个对象 1 个 RTT。
2. **流水线方式**：可以连发多个请求不等应答，进一步减少 RTT。

流水线仍然只在**同一条** TCP 连接上连发多个请求，不会开多条 TCP 连接。

浏览器另有一种**并行连接**：同时开多条 TCP 连接，各取各的对象。

流水线省 RTT 是因为省掉了"等前一个响应回来再发下一个"的等待，不是因为有并行连接。

**流水线的限制**：虽然流水线可以连发多个请求，但同一条 TCP 连接的实际发送速度仍受拥塞控制约束：发送方必须遵守拥塞窗口 cwnd 的逻辑，窗口内最多只能发送 cwnd 大小的数据，发完要等确认（ACK）窗口前移才能继续发下一批。所以流水线不能"无限连发"，还是要等 TCP 确认来推进窗口。

**例题**：一条持续连接，某对象共 8 个（1 个 HTML + 7 个图片），采用流水线方式，在同一条 TCP 连接上连发请求。假定这条连接的拥塞窗口允许每轮 RTT 最多传输 4 个对象的响应数据（cwnd 限制的是在途字节数，这里换算成对象数便于计算）。已知 RTT = R，传输对象的时间忽略不计。问取回全部 8 个对象需要多少个 RTT？

**解析**：流水线在同一条连接上也不能违背拥塞窗口——每轮最多传 4 个对象。第 1 轮传 4 个（第 1 到第 4 个对象），等 1 个 RTT 的 ACK 窗口才前移；第 2 轮再传 4 个（第 5 到第 8 个对象），再等 1 个 RTT。共需要 **2 个 RTT** 全部取回。若不用流水线，每发 1 个等 1 个 RTT，需要 8 个 RTT。

#### Cookie——让无状态的 HTTP 记住状态

HTTP 本身是**无状态协议**，服务器不记得两次请求来自同一个用户。Cookie 让浏览器在请求里自动带一小段文本数据（`Cookie` 首部），服务器据此在多次请求之间识别同一个用户。

**Cookie 工作四步**：

1. 服务器在响应里加 `Set-Cookie` 首部。
2. 浏览器把 Cookie 存下来。
3. 之后每次访问该站点，浏览器在请求里自动加 `Cookie` 首部。
4. 服务器读 Cookie 识别用户。

Cookie 可以设有效期（Expires/Max-Age）、域名范围（Domain）和路径范围（Path）。

> 💡 **Cookie 的经典应用**
>
> 购物车、登录态保持、用户偏好记录。Cookie 只是存在客户端的小文本文件，不是程序，不能跨域名读取其他站点的 Cookie。
