# TCP

> 《计算机网络》· 传输层

### TCP 结构(重要度:★★★★★)

#### TCP 的特点

TCP（Transmission Control Protocol）是传输层面向连接的可靠传输协议，和 UDP 并列。它的 5 个特点：

**① 面向连接**：通信前必须先通过三次握手建立连接，通信结束后四次挥手释放。连接是一对一的，一条 TCP 连接只能是两个端点之间的通信（不支持广播、多播）。

**② 可靠交付**：保证应用进程收到的数据无差错、不丢失、不重复、按序到达。通过序号、确认、重传、校验、窗口等机制联合实现。

**③ 全双工通信**：通信双方可以在同一条连接上同时发送和接收数据。双方各自维护发送缓冲区和接收缓冲区，数据可以两个方向独立流动。

**④ 面向字节流**：TCP 把应用层数据看作一串连续的字节流。应用一次给 100 字节还是 10 次 10 字节，对 TCP 没有区别，TCP 会按自己的节奏（MSS、窗口）封装成若干报文段发出。

**⑤ 一对一连接**：TCP 的连接由"源 IP + 源端口 + 目的 IP + 目的端口"四元组唯一确定，两端各有且仅有一个对端。UDP 则是无连接，可以一对多。

> ⚠️ **易错点：面向字节流 vs 面向报文**
>
> UDP 是面向报文的：应用层给多少，UDP 就给多少封装成一个 UDP 数据报，不合并也不拆分。TCP 是面向字节流的：应用交下来的是字节流，TCP 可能拆分、合并、分包，只要字节序号对得上就可以。所以接收方 TCP 提交给应用的数据边界和发送方 write 调用的次数没有任何对应关系。

#### TCP 首部结构

TCP 报文段由**首部**和**数据**两部分组成。首部最小 20 字节、最大 60 字节，其中选项最多 40 字节，用 0 填充补齐到 4 字节整数倍。

![示意图](attachment://vault/3af9f289-a1ac-4b17-af50-f57364853d53/kb-tcp-hdr-2.svg)

**源/目的端口**（各 16 bit）：标识发送和接收的应用进程。加上 IP 首部的源/目的 IP 地址，构成唯一标识一条连接的"四元组"。

**序号 seq**（32 bit）：TCP 按字节编号。seq 字段的值是本报文段所携带数据部分第一个字节的编号。建立连接时双方各自随机选一个初始序号 ISN。

**确认号 ack**（32 bit）："期望收到对方下一个报文段数据部分第一个字节的序号"。ack-1 及之前的所有字节均已正确收到。ACK 标志为 1 时该字段才有效。

**数据偏移**（4 bit）：即 TCP 首部长度除以 4。范围 5 到 15，对应首部长度 20 到 60 字节。因为可选项长度可变，接收方用这个字段定位数据部分的起始位置。

**窗口 rwnd**（16 bit）：接收方告诉发送方"我还能收多少字节"，以本报文段的确认号为起点计算。窗口字段用于流量控制，发送方不能发送超过 rwnd 的数据。

**校验和**（16 bit）：和 UDP 一样，TCP 的校验覆盖"伪首部 + TCP 首部 + TCP 数据"。不同的是，TCP 校验和在 IPv4 下是强制的。

**紧急指针**（16 bit）：仅在 URG=1 时有效，指向本报文段中紧急数据最后一个字节的偏移量。可让接收方优先处理紧急数据。

**选项**（0 到 40 字节，4 字节对齐）：常用选项包括 MSS（最大报文段长度）、窗口扩大因子（让 rwnd 字段左移）、时间戳（用于 RTT 估算）、SACK（选择性确认）等。填充用 0 补齐到 4 字节整数倍。

**URG**（紧急位）：URG=1 表示本报文段含有紧急数据，紧急指针字段有效。TCP 把紧急数据插到本报文段数据部分最前面，发送方应绕过发送缓冲优先发送。

**ACK**（确认位）：ACK=1 表示确认号字段有效。连接一旦建立，所有报文段的 ACK 必须为 1。ACK 可以捎带——如果本端也有数据要发，就合并在同一个报文段里。

**PSH**（推送位）：PSH=1 表示希望接收方一收到就立刻将数据提交给应用进程，不要在缓冲里攒着。常用于交互式应用。

**RST**（复位位）：RST=1 表示出现严重错误（如端口没人监听、连接异常），必须立刻释放连接重新来过。RST 不需要确认，不需要挥手。

**SYN**（同步位）：SYN=1 表示连接请求或连接接受报文段。SYN 即使不携带数据也要消耗一个序号。

三次握手中：

1. 第一次：只有 SYN=1。
2. 第二次：SYN=1 且 ACK=1。
3. 第三次：只有 ACK=1，可以携带用户数据。

**FIN**（终止位）：FIN=1 表示发送方数据已发完，请求关闭本方向发送通道。FIN 即使不携带数据也要消耗一个序号。

四次挥手：

1. 主动方发 FIN。
2. 被动方回 ACK。
3. 被动方发 FIN。
4. 主动方回 ACK。

> ⚠️ **纯 ACK 不占序号**
>
> 只有 SYN 和 FIN 即使不带数据也各占 1 个序号。一个纯 ACK（只置 ACK=1，不携带数据，也没有 SYN/FIN）不消耗任何序号，下一次再发seq还是不变，它的 seq 只是登记下一个待发字节的编号，对方无须再对它确认。

### TCP 连接管理(重要度:★★★★★)

#### 三次握手

TCP 建立连接的过程称为三次握手，目的是让双方确认对方收发能力正常、协商初始序号 ISN 和 MSS 等选项。

**第一次**：客户端 CLOSED → SYN-SENT。发送 SYN=1, seq=x（随机 ISN），SYN 消耗 1 个序号。

**第二次**：服务端 LISTEN → SYN-RCVD。收到 SYN 后分配 TCB，回 SYN=1, ACK=1, seq=y, ack=x+1。SYN+ACK 消耗 1 个序号。

**第三次**：客户端收到 SYN+ACK 后进入 ESTABLISHED，回 ACK=1, seq=x+1, ack=y+1。这次 ACK 可携带应用数据，不带数据则不消耗序号。服务端收到后也进入 ESTABLISHED。

![示意图](attachment://vault/3af9f289-a1ac-4b17-af50-f57364853d53/kb-tcp-hs-svg.svg)

#### 四次挥手时延图

TCP 是全双工的，两个方向要分别关闭。任一方先调用 close() 主动关，发 FIN 把本方向发送通道关掉；对方 ACK 后，等自己数据也发完再发 FIN。

**第一次**：主动方 ESTABLISHED → FIN-WAIT-1。发送 FIN=1, ACK=1, seq=u, ack=k（消耗 1 个序号）。

**第二次**：被动方收到 FIN 后，回 ACK=1, seq=k, ack=u+1。被动方进入 CLOSE-WAIT，主动方收到后进入 FIN-WAIT-2。此后被动方还可以继续向主动方发送剩余数据。

**第三次**：被动方数据发完后调 close()，发 FIN=1, ACK=1, seq=w, ack=u+1（消耗 1 个序号）。被动方进入 LAST-ACK。

**第四次**：主动方收到 FIN 后，回 ACK=1, seq=u+1, ack=w+1（不占序号）。主动方进入 TIME-WAIT 等待 2MSL 后才 CLOSED。被动方收到 ACK 后直接 CLOSED。

主动关闭方要等 2MSL，有两个原因：

**① 保证最后一次 ACK 能到达对方**。主动方发完最后的 ACK 后，如果这个 ACK 在网络中丢失，被动方会一直停在 LAST-ACK，反复重传它的 FIN。

主动方等待至少 2MSL（一个 MSL 够 FIN 传过来，一个 MSL 够 ACK 传回去），才能等到重传的 FIN 并再补一次 ACK。如果不等就直接 CLOSED，被动方永远等不到确认，无法关闭连接。

**② 让本连接的所有旧报文段在网络中消失**。MSL 是报文段在网络中的最长存活时间（超过即被丢弃）。等 2MSL 可以保证上一次连接里迟到、被复制或迷路的报文段（比如某个延迟了很久的数据段）都已经在网络中消失，不会混进下一次使用同一组端口号的新连接里，避免新旧连接数据混淆。

> ⚠️ **2MSL 速记**
>
> 等 2MSL = ① 给最后那个 ACK 留够往返时间，让被动方能重发 FIN 时能收到；② 让本连接的旧报文段全部超时消失，不给新连接"留垃圾"。主动关闭方等待，被动关闭方不用等。

### TCP 可靠传输(重要度:★★★★★)

#### TCP的序号

TCP 的序号是**按字节**编号的，不是按报文段编号。每个报文段里的 seq 字段表示"本报文段携带的数据中第一个字节的编号"。确认号 ack 表示"期望收到的下一个字节的编号"，等价于"ack - 1 及之前的所有字节都已正确收到"。

序号的作用在可靠传输里体现在 3 件事上：

**① 去重**：网络里如果某个报文段被复制了，或超时重传又和原来的都到达，接收方可以根据序号判断"这个字节我已经收到过了"，直接丢重复的。

**② 排序**：IP 网络不保证按序到达，后发的报文段可能先到。接收方把到达的字节按序号排好，缺的先留在接收缓冲里，等缺失的字节到齐了再一起交给应用，保证应用看到的是按序字节流。

**③ 确认**：接收方用确认号 ack 告诉发送方"我已经收到哪了"。发送方知道哪些序号范围内的字节已经确认，就可以把这些字节从发送缓冲里清掉。

> ⚠️ **SYN/FIN 占序号，纯 ACK 不占**
>
> 第一次握手中的 SYN 和 FIN 即使不携带任何数据也要消耗 1 个序号。一个纯 ACK（没有数据、没有 SYN/FIN）不消耗任何序号，对方不需要对它再做确认。

#### 累计确认与捎带确认

TCP 的确认是累计确认：ACK n 表示 n - 1 及之前的所有字节都已正确收到。如果确认号是 2001，就意味着 1 到 2000 这 2000 个字节接收方都有了，下一个想要的是 2001 号字节。

累计确认的好处：哪怕中间某些 ACK 丢了，只要后面有一个更大编号的 ACK 到达发送方，前面那些字节也就"相当于都确认了"。比如 ACK1001 丢了，但后面 ACK2001 到了，就说明 1 到 2000 都收到了，发送方不需要关心 ACK1001 到没到。

![示意图](attachment://vault/3af9f289-a1ac-4b17-af50-f57364853d53/kb-tcp-rel-ack-3.svg)

捎带确认（Piggybacking）：如果接收方收到对方数据后，恰好本端也有数据要反方向发，就把 ACK 字段顺带塞进自己的数据报文段里，不用单独发一个纯 ACK 报文。这样省去一个报文，提高信道利用率。

![示意图](attachment://vault/3af9f289-a1ac-4b17-af50-f57364853d53/kb-tcp-rel-ack-5.svg)

#### 超时重传和冗余 ACK 快重传

TCP 有两种方式触发重传：

1. **超时重传**。
2. 收到三个重复 ACK（冗余 ACK）触发**快重传**。

408 只要求掌握它们的思想，不考具体 SRTT/RTTVAR 公式。

**超时重传**：发送方为每一个已发出但未确认的报文段维护一个**重传计时器**。如果计时器到期了，对应的确认还没到，就判定报文段丢了，重传该报文段并把超时时间翻倍（"指数退避"）。

超时重传最大的缺点：需要等到 RTO 超时才重传。RTO 通常比实际 RTT 大，经常几百毫秒，对于应用来说太慢。所以 TCP 还有一条更快的重传机制：**快重传**。

**冗余 ACK**（Duplicate ACK）：接收方收到失序的报文段（比如前面缺了一段）时，不给失序段回确认，而是立刻再发一个"我还是想要那个缺失字节"的 ACK。这个 ACK 的序号和之前发过的 ACK 一样，就叫**冗余 ACK** 或**重复 ACK**。

**快重传算法**：发送方一旦连续收到 3 个相同的冗余 ACK，就判定对应的报文段已经丢失，不必等待重传计时器超时，立刻重传那个缺失的报文段。

### TCP 流量控制与拥塞控制(重要度:★★★★★)

#### 发送窗口由两个窗口共同决定

TCP 发送方一次能发多少，是"接收方撑得下"和"网络装得下"这两个限制里取更小的那个：

$$
\text{发送窗口上限} = \min(\text{rwnd},\ \text{cwnd})
$$

**rwnd（Receiver Window）接收窗口**：接收方根据自己接收缓冲的剩余空间，在每个 ACK 的 16 bit 窗口字段里告诉发送方"我还能收 rwnd 字节"。这是流量控制。

**cwnd（Congestion Window）拥塞窗口**：发送方根据自己对网络拥塞程度的判断，动态维护的一个值，表示"我觉得我最多再发 cwnd 字节就不会把网络塞爆"。这是拥塞控制。

**例题**：主机甲向主机乙发送一个 TCP 段，序号 seq=201，数据 200 字节。乙正确收到该段后回复确认。

乙的接收缓存总大小为 3000 字节，该段到达前缓存中已有 1200 字节数据未被乙的应用取走。假设 cwnd 足够大。回答：

(1) 乙回复的确认号 ack 是多少？

(2) 乙回复的窗口字段 rwnd 填多少？

(3) 甲收到确认后，发送窗口上限是多少？还能立即再发多少字节？

**解析：**

(1) 序号 201 + 数据 200 字节 = 覆盖字节 201 到 400，乙期望下一个是 401，故 ack = 401。

(2) 接收缓存已占用 = 1200 + 200 = 1400 字节，空闲 = 3000 − 1400 = 1600 字节，故 rwnd = 1600。

(3) 发送窗口上限 = min(rwnd=1600, cwnd) = 1600 字节。已发未确认字节 = 0（201 到 400 已被 ack=401 确认）。还能发 1600 字节。

#### 零窗口与窗口探测报文段

如果接收方接收缓冲已经全部占满，它在 ACK 里会把 rwnd 填为 0，这叫**零窗口通告**。发送方收到 rwnd=0 必须立刻停止发送任何数据。

接收方应用读取了一些数据、释放缓冲后，要主动告诉发送方"我又有空间了"。这条通知是**纯 ACK**（窗口更新），不携带数据。

如果"窗口更新"的 ACK 在网络里丢了，发送方永远以为窗口是 0，接收方永远以为自己已经通知过了，双方就死锁。TCP 专门设计了**零窗口探测报文段**（Zero Window Probe）来打破死锁。

**零窗口探测的做法**：发送方维护一个坚持计时器（Persist Timer），对方通告零窗口时启动。计时器到期后发一个 1 字节的探测报文，接收方必须回 ACK。

1. ACK 里窗口还是 0：坚持计时器翻倍（指数退避），最长一般 60 秒不再翻倍。
2. 某次 ACK 里 rwnd>0：立即按新窗口继续发送。

#### 拥塞控制四种算法

拥塞控制看 cwnd 怎么变，考纲只要求经典的 Tahoe/Reno 四个算法：

1. **慢开始**（Slow Start）。
2. **拥塞避免**（Congestion Avoidance）。
3. **快重传**（Fast Retransmit）。
4. **快恢复**（Fast Recovery）。

慢开始和拥塞避免是"增长阶段"，快重传和快恢复是"丢包时怎么处理"。

关键参数：**ssthresh**（慢开始门限）。

1. cwnd < ssthresh：走慢开始。
2. cwnd ≥ ssthresh：走拥塞避免。

**慢开始**（指数增长）：刚连接或刚从 RTO 恢复时，cwnd=1 MSS。每过一个 RTT，cwnd 翻倍（1→2→4→8→16...）。名字叫"慢开始"是因为从 1 起步，不是线性。

**拥塞避免**（加法增长）：cwnd 达到 ssthresh 后放缓，每过一个 RTT 只 +1 MSS。趁网络还没丢包先保守试探。

丢包时有两种处理方式：

**RTO 超时**（严重丢包）时：

1. ssthresh = cwnd/2（至少为 2）。
2. cwnd = 1 MSS。
3. 从慢开始重新跑。

这是最狠的惩罚。

**3 个冗余 ACK**（快重传 + 快恢复）时，网络还没彻底堵死：

1. ssthresh = cwnd/2。
2. cwnd = ssthresh。
3. 重新进入拥塞避免（加法增长）。
